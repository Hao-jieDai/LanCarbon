# RAG 更新与故障处理指南

本文件是新对话接手 LanCarbon 资料问答时的固定入口。结合 [当前状态](rag-handoff.md) 和根目录 [AGENTS.md](../AGENTS.md) 阅读；后续产品阶段见 [项目接手说明](project-handoff.md)。历史试验已从工作树移除，必要结论归入本文，过程可从 Git 历史查询。以最新用户指令、当前状态和实际代码为准，不依赖上一轮对话记忆。

## 1. 当前目标与已经作出的决定

当前目标是**基于用户选定资料的辅助阅读问答**：定位内容、解释概念、比较文献，并提供回到原文的引用。关键金额、单位、公式变量、主体归属和跨文献可比性仍需要用户核对原文。用户已明确接受这一用途；不是承诺模型的每句话都正确。

当前采用 PaperQA 全文方案，默认使用用户自己选择的模型，现有使用偏好是 Flash；模型不写死，也不自动切换。不要因为一次语义错误就重搭 RAG、追加一条提示词或开启反复付费试验。软件自身可复现的故障仍必须修复。先前未通过的学术测试保留为未通过，不因用途调整改写结果。

本指南的 RAG 流程已按 2026-10-29 的 2.5.4 代码复核；本轮增加随页 Chat 来源绑定与可选 contextNoteId 会话归属，不改动解析、全文组织、提示词或模型调用流程。安装状态、最终提交、包摘要和备份位置见当前状态。今后升级时同步更新本文的流程快照；不要把本文的数字或路径名称当作不可变实现。

写作侧栏入口在 `src/shared/writingWorkspace.ts`、`src/components/WritingChat.tsx`。默认当前页，章节范围包含所属顶层章节和后代，整本范围使用 Book ID；发送前先保存工作区，再复用 ai:set-sources 与 ai:send。会话的 contextNoteId 由 AIChatStore 校验和持久化，旧会话无此字段也可正常读取。不能从当前界面页或全局最后聊天 ID 猜测正在生成回答的所属页面。

Chat 共用输入卡片与图标工具栏。Workshop 默认仅列出无 contextNoteId 的独立会话，顶部 Workshop / Chat 旁的 Chat / Page chats 切换按钮 单独列出全部随页会话，允许继续提问、调整来源、导出和删除。两个列表更新时必须保留另一类记录；不要迁移、重建或删除旧 JSON 来实现分类。页面侧栏继续按当前 Note 过滤；Workshop 的随页分类使用会话原有来源，不擅自绑定正在编辑的页面。修改后应运行 tests/chat-layout.test.tsx 及 tests/e2e/chat-layout.spec.ts，核对分类／删除同步／来源／窄窗口提示宽度。

## 2. 实际运行流程及代码入口

```text
选择 Notes / Books / Library 来源
  → 识别来源、检查文件变化与解析状态
  → 本地提取全部可用文本（必要时本地 OCR）
  → PaperQA 本地组织原文、问题及同范围近期历史
  → 当前选定 Chat 模型的一次流式回答
  → 本地计算标记渲染、来源和引用检查
  → 保存正文 / Thinking / 原文证据 / 用量
  → 显示、复制、导出及引用跳转
```

| 环节 | 当前职责 | 优先检查的文件 |
| --- | --- | --- |
| 路径选择 | 安装版或 PaperQA 开发模式使用 PaperQAGrounder；普通开发启动仍可能走旧检索路径 | `electron/main.ts`、`scripts/dev-paperqa.cjs` |
| 来源与范围 | Notes、Book 页面、Library、附件及排除项；稳定来源 ID、指纹、范围隔离 | `electron/knowledge-sources.ts`、`src/shared/knowledge.ts`、`src/shared/grounding.ts` |
| 解析与缓存 | 文本提取、处理状态、指纹检查、本地语料与 OCR | `electron/knowledge-store.ts`、`electron/knowledge-extractor.ts`、`electron/knowledge-worker.ts`、`electron/knowledge-epub.ts`、`src/knowledge-parser.ts`、`electron/ocr-store.ts` |
| 全文组织 | 选定资料完整性、超限停止、同范围历史、发送前再次核对来源 | `electron/paperqa-grounding.ts` |
| PaperQA 适配 | 本地 Python 桥接、原生全文上下文组织、回答模板；不持有模型密钥，不调用模型 | `electron/paperqa-bridge.ts`、`scripts/paperqa_prompt.py`、`scripts/paperqa_full_context.py`、`scripts/paperqa_evidence.py` |
| 请求与用量 | 当前连接/模型、用户共享规范、流式输出、取消、接口错误、用量记录 | `electron/ai-service.ts`、`electron/ai-client.ts`、`electron/ai-storage.ts`、`src/shared/chatText.ts` |
| 原文金额计算 | 原文匹配、单位识别、确定性算术、旧协议兼容 | `electron/chat-calculations.ts`、`electron/chat-quantities.ts` |
| 引用与显示 | 当前来源状态、标签、原文定位；全文路径不运行旧的自动单位修补 | `electron/chat-grounding.ts`、`src/components/AIChat.tsx` |
| 存储与导出 | 独立聊天文件、去重证据、旧数据兼容、导出一致性 | `electron/ai-storage.ts`、`electron/ai-chat-files.ts`；由界面入口追踪对应导出实现 |

**不要仅凭文件名判断生效路径。** `chat-policy.ts`、旧 `ChatGrounder.prepare()` 和其他历史检索/修补模块仍存在，但安装版资料问答由 `PaperQAGrounder` 组织。修改旧路径不能当成已经修好当前安装版。先检查 `main.ts` 的实际选路，再检查最终发送的 messages。

当前全文模式不使用 Embedding/Rerank、问题规划、模型摘要、二次改写或评判模型。已有检索配置和旧聊天标签仍保留。Python 适配器使用 PaperQA 的上下文组织能力；模型请求由 Electron 统一发送，所以网络、取消和用量沿用 LanCarbon。

开发全文流程时先执行 `npm run setup:paperqa`，再用 `npm run dev:paperqa`（或 `Start-PaperQA-Dev.cmd`）。开发窗口标题含 **PaperQA Development**，默认使用 `.dev-workspace/PaperQA` 的独立数据；先核对环境覆盖项，不读取日常配置做试验。模型不限于 Flash，使用用户选择且已配置的连接。安装版自带运行环境；变更依赖时同时核对 `scripts/paperqa-requirements.txt`、`scripts/paperqa-runtime-lock.txt` 和打包资源。

Python 子进程不持有模型密钥、不发起网络调用，仅组织原文和请求。Electron 负责唯一生成请求、取消及计费。聊天采用独立会话文件与共享证据；不要恢复旧的逐消息重复存储全文方式。Chat 的 Copy、PDF 和 Note 导出应保留正文、可选 Thinking 和引用对应关系；导出不调用模型。

当前边界：最多 500,000 字符、999 个原文片段；消息序列化后不超过 750,000 字节；同一资料范围的近期已完成历史最多 6 条消息、20,000 字符。超限、缺失或部分解析时停止，不静默截掉选定原文。这些限制须以源码复核，不能直接解释成“固定可选多少篇文献”。全文是解析出的文字，不等于视觉表格和公式已无损识别。

## 3. 提示词职责：不要继续分散追加

| 内容 | 所属位置 | 修改前必须确认 |
| --- | --- | --- |
| 用户语气、格式与当前模型身份 | AI 设置；`ai-service.ts` / `src/shared/chatText.ts` | 保留用户规范；不要把模型身份从历史回答继承过来 |
| 资料回答、部分可答、引用格式和原文定义 | `scripts/paperqa_prompt.py` 的回答模板及 PaperQA 输出的消息 | 比较最终 payload；不要同时在旧检索策略中重复加入同一规则 |
| 原文、来源顺序及近期历史 | `paperqa-grounding.ts` 与全文适配器 | 它们是资料，不是指令；旧回答不是新的事实证据 |
| 本地计算语法 | `chat-calculations.ts` | 只约束可执行计算，不认证经济含义；不放入特定论文数字或答案 |

确有通用指令冲突时，优先删除重复、矛盾或已失效的规则，明确唯一职责位置。不得在来源解析、提示词、渲染器三处分别写同一个论文结论。不能为让某一道题通过而改变默认模型、偷偷增加调用、让答案在后台重写。

## 4. 金额机制：检查了什么，没有检查什么

- 新回答使用 `quantityProtocol=3`。模型提供来源标签与原文金额文字，程序在指定来源内做唯一匹配；只允许有限的排版空白、断词归一，不模糊匹配数字、不补币种、不猜量级。
- 唯一且明确的操作数才能做同币种换算、差额和降幅。成功时保留原文金额与计算结果。匹配失败时不把正常正文换成占位金额；保留已匹配原文，并在检查区域说明计算未完成。完全无法匹配的计算不能冒充原文。
- 内部仍可保存由程序生成的位置 ID 作为运算记录；不再要求模型生成这些偏移编号。
- `checked` 仅表示已解析计算的算术通过，不是整篇回答或情景/主体归属通过。`not-checked` 不等于错误；普通原文复述没有计算标记时也不会获得语义认证。
- `quantityProtocol=1/2` 和旧检查结果继续读取，旧聊天不自动重写。旧版程序不能读取新版协议时，回滚必须配套恢复升级前的数据备份。

相关通用回归：`tests/chat-quantities.test.ts`、`tests/chat-calculations.test.ts`、`tests/paperqa-grounding.test.ts`、`tests/ai-chat-files.test.ts`。它们覆盖不同币种、数字、换行、断词、歧义、错误出处、零基数、流式片段和旧记录，不能替代真实模型学术评价。

## 5. 重大问题先怎样定位

先保护现场和数据，不删除聊天、不清空资料库、不覆盖原文。记录版本、提交、模型 ID、来源范围、问题和出错句；读取配置时不要输出密钥或整个设置文件。

| 现象 | 对照哪两份内容 | 定位结论与处理 |
| --- | --- | --- |
| 原文有而回答说没有 | PDF 原页／EPUB／Markdown 与解析文本，再比较最终发送原文 | 解析缺字、表格错位、OCR 错误、范围漏项分别修复；不能直接归咎模型 |
| 读了另一篇或用了旧内容 | 选择树、稳定 ID、指纹、发送前后的来源状态及历史范围 | 检查来源识别、缓存失效和范围隔离，不拿同名文件当同一来源 |
| 数量缩小/放大、单位错配 | 原文字符及量级、模型原始正文、本地显示/导出 | 显示相对原始输出改坏时修软件；模型已选错主体/情景时，正确算术不能替它证明选值正确 |
| 公式或概念解释错误 | 原页定义、实际发送内容、原始回答 | 已提供的正确原文被模型误解，记录为生成问题；若符号或定义在解析中丢失，则是解析问题 |
| 引用打不开或指向错误页 | 保存的标签、原文片段、来源指纹和 anchor | 检查身份/页码/行号映射，保留当时证据，避免跳转到已变更原文 |
| 保存失败、重启丢失、导出不同 | 原始输出、最终正文、聊天/证据文件、导出载荷 | 按数据一致性故障处理；先备份，优先离线重现，不要求用户重新付费生成答案 |
| 慢、429、超时、Thinking 没正文 | 准备耗时、首字节时间、网络错误、finish_reason、usage | 区分本地准备、代理/服务端和生成；失败也可能产生费用，不自动换模型或重试收费 |

**定位证据至少要区分五层：原始文档 → 解析文本 → 实际请求 → 原始模型输出 → 显示/保存结果。** “完整原文已发送”不能只靠界面标签判断；“是模型的问题”也不能只因为截图里答案错了就下结论。没有保留请求或原始输出时，应明确哪些环节尚无法排除，不能编造完整因果链。

## 6. 修复与验证的有限流程

1. **核对现状。** 读取交接和 Git 状态、版本、安装包摘要；检查实际生效路径。尊重用户正在进行的其他改动，不擅自重置工作区。
2. **写一条可验证的假设。** 明确哪个环节、什么通用输入导致问题，以及什么结果将证明假设不成立。先把已有失败输出离线重放，避免重复付费。
3. **最小实现。** 不硬编码作者、论文名、固定题目或预期答案；一般化规则必须能解释无关领域、不同数字/措辞的案例。私有完整材料只放忽略的 `acceptance/`；长期测试只提交必要的去标识最小样例。
4. **离线验证。** 执行 `npm run test:rag`、`npm run typecheck`；涉及 IPC、界面、存储、导出或打包时做相应临时数据/模拟接口桌面测试。不要为了通过测试而同步把错误结果改成期望值。
5. **只有需要时才做真实验证。** 先限定问题、资料、最终候选、最多调用数、价格与预算、通过条件和停止条件。用户已有的有效授权可沿用，不重复索取；但已关闭账本或明确停止的任务不能因新对话而自行重启。不得擅自加评判/改写服务或第二次模型调用。
6. **触发停止就停。** 假设被否定、语义错误仍存在、预算/调用上限到达或用量不明无法保证余量时，停止并交代具体结果。不要靠更换措辞、材料或反复采样直到一次碰巧通过。新的不同假设属于新方案，要先向用户解释，而不是无限延长原试验。
7. **如实交付。** 区分单元测试、模拟桌面、真实模型、原始输出的离线重渲染、实际安装验证。没有执行的原五篇或新材料验收不得写成通过；重放旧输出不能写成新模型回答。

不对全部任务设一个机械的“一次失败永远停用”规则。停止的是没有证据支持继续投入的当前修复/试验路线；明确的软件故障可以按新的定位结果修复。用户认可的辅助阅读用途也不能用来掩盖软件改坏数据或确定性运算错误。

## 7. 数据、预算与发布保护

- 日常根目录可能被用户改变，先读取当前数据位置；本机路径快照见当前状态。聊天正文和去重证据位于数据目录下 `Research/Chats`，不应复制整份证据到每条消息制造存储膨胀。
- API Key 由 Electron 的密钥存储保护。日志、提交、问题报告、截图和导出不得包含明文密钥。测试用隔离数据；需要真实调用时按授权复用配置，禁止输出完整配置或密钥材料。
- 真实费用记录成功、失败和未知用量；保留实际 usage、价格依据、估算与平台实扣的区别。未知费用保守预留，不因失败或开新对话而清零预算。参考账本可能包含隐私，只在本机查看必要字段。
- 历史试验账本已关闭，`STOP` 保留。文档、安装或清理任务不因此获得新的付费范围；必要真实验证按用户明确授权及本轮上限执行，不重复沿用历史余额或扩大后台调用。
- 安装前确认软件关闭，备份 Data、Library、Config 与所需密钥解密状态，校验副本；安装后核对个人 Notes/Books、聊天、Thinking、配置、用量、原文、任务栏/快捷方式。不要借升级清理用户材料。
- 每次代码修改提交 Git；更新 ReadMe 和交接。功能/流程变化同步长期教程，Bug 和内部实现只进 ReadMe。版本以用户当前决定为准，安装包清理遵守 AGENTS.md。创建 Release 草稿、Tag、推送和正式发布需要对应的明确指令，不能把“安装更新”当作发布授权。

## 8. 每次交接必须留下什么

更新 `rag-handoff.md` 的现状，替换已经过时的内容；旧状态由 Git 历史保存，不再次堆叠版本日志。长期规则更新本文，阶段性产品计划更新项目接手说明。至少写清：

- 用户目标、已授权范围、仍有效的限制及是否允许安装；
- 当前版本、代码提交、实际生效路径、安装状态和备份位置；
- 故障层级、可复现证据、假设、通用修复及没有修改的边界；
- 实际执行的检查和结果、未执行的检查、剩余问题；
- 真实调用次数、已用费用、剩余预算和账本是否关闭；
- 下一步具体动作及停止条件，不写“继续测试直到通过”；
- 安装包摘要、保留回滚版本，是否提交/推送/发布。

新对话可从这句话开始：

> 请先阅读 `docs/rag-update-guide.md`、`docs/rag-handoff.md` 和 `AGENTS.md`，核对当前代码与版本。针对我描述的问题先定位解析、来源/上下文、生成、渲染或存储中的具体环节，说明通用修复方案及验证边界，不针对论文打补丁，不自动调用真实 API 或重启已关闭的试验。

## 9. 已结束试验留下的维护结论

这些是有限试验的决策依据，不是对所有材料或模型的普遍性能排名。原始过程可通过当前状态中的 Git 历史入口查询。

- **先提供正确原文，再判断生成问题。**曾发现解析、目录漏项、资料识别和上下文遗漏等软件故障；也有完整证据正确进入请求后仍出现主体、情景或公式解释错误的情形，不能全部归因于某一个环节。
- **中间处理不是越多越好。**逐篇模型笔记、定位表、局部事实核对、规划与覆盖检查等候选未稳定解决问题；额外调用和失败成本增加，因此没有纳入当前全文流程。重新考虑时必须提出新的证据与小规模停止条件。
- **保留全文优先的选择，不承诺其消除语义错误。**成熟框架比较最终采用 PaperQA 全文组织；其他候选未达到当时需求，不代表这些框架普遍不可用，也不授权重复大规模安装评测。
- **不要让模型编造内部数值编号。**旧强制编号及目录机制存在漏项、选错引用等风险；现用原文金额与来源唯一匹配。程序能证明的只是匹配和算术，不是经济主体或条件关系。
- **不把模型价格当作质量证据。**曾做 Flash、Pro 和其他模型对照，不能从少量问题推出固定排名。保留用户模型选择；更换模型或增加输入必须说明费用影响，不能以未验证的模型承诺替代故障定位。
- **保留来源范围和自然表达。**支持可回答的部分，APA 作者年份与可点击证据链接各司其职；不要重复输出“我的解读”“摘录没有不代表实际没有”等免责声明，也不要为改善风格删除必要限定或改写历史回答。
- **保留测试，而非堆积试验日志。**不同材料/措辞的通用回归继续在 `tests/` 维护；删除旧说明不删除测试、脚本、代码或用户数据，不把历史未通过改写为通过。

### 桌面测试路径

`tests/e2e/grounded-chat.spec.ts` 验证开发态的旧检索路径，包含 Embedding、Rerank 和规划调用断言；设置 E2E_EXECUTABLE 时跳过。安装版实际采用 PaperQA，应执行 `tests/e2e/paperqa-dev.spec.ts`。`tests/e2e/writing-workspace.spec.ts` 同时支持开发与打包路径，核对随页来源、最新编辑、标签状态和会话归属。模型响应均可用本地模拟接口验证，不能据此宣称真实模型学术验收通过。
